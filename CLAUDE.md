# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Playwright automation script that logs into Daater (app.daater.co, a trade-data platform), searches for a fixed list of tariff codes (`tariff-codes.json`) against Colombia's "DAATER ONLINE 2025-2026" import database, downloads the result as an `.xlsx` backup into `output/`, and loads the parsed rows into a Postgres database (Supabase) that accumulates across weekly runs.

On top of that database sits a dashboard (`server.mjs` + `public/`, deployed to Vercel) that visualizes the imports — by molecule (active ingredient), brand, month, tariff code, country of origin, and importer. Molecule/brand aren't columns Daater provides directly: they're extracted from the free-text `Desc Completa De Producto` field (INVIMA regulatory paragraphs) via `product-extractor.js`, with a manual-override mechanism for cases the regex gets wrong.

There is no build step or test suite — this is a set of standalone Node scripts run directly. The scraper (`search-daater.mjs`) is intended to run manually about once a week, from a local machine, and writes directly to Supabase over the network; the dashboard runs on demand (locally via `npm run dashboard`, or live at all times on Vercel).

## Commands

```
npm install              # also runs postinstall -> playwright install chromium
npm run search           # runs node search-daater.mjs (scrape Daater, update Supabase)
npm run dashboard         # runs node server.mjs — dashboard at http://localhost:4321

node backfill-products.mjs   # (re)compute molecula/marca/extraction_confidence for ALL rows in Supabase
node review-products.mjs [N] # print the N (default 30) distinct descriptions with lowest-confidence extraction, to guide product-overrides.json edits
```

Setup before running the scraper or dashboard locally: copy `.env.example` to `.env.local` and fill in `DAATER_EMAIL` / `DAATER_PASSWORD` / `DATABASE_URL`. The script exits early with a Spanish error message if the Daater credentials are missing; `db.js` throws if `DATABASE_URL` is missing.

`DATABASE_URL` must be Supabase's **connection pooler** string (Supavisor), not the direct `db.<project-ref>.supabase.co` host — the direct host only resolves to an IPv6 address in at least this project's case, which `getaddrinfo`-fails from Vercel's serverless network (no IPv6 egress) and may fail from other networks too. Get the pooler string from the Supabase dashboard → **Connect** button (top of the project page) → a host like `aws-<n>-<region>.pooler.supabase.com`, port `5432` (session mode) or `6543` (transaction mode), user `postgres.<project-ref>` (not just `postgres`). Confirm it resolves to an IPv4 address (`nslookup <host>`) before trusting it.

There is no lint or test command configured.

## Architecture

- **config.js** — the only place to change run behavior: target `country`, `flow` (`IMPORTACIONES`/`EXPORTACIONES` tab prefix), `baseFilter` (restricts the run to one base tab, e.g. `'DAATER ONLINE 2025-2026'` — set to `null` to iterate all bases), `showDetail`, `outputDir`, and `backfillRange` (the explicit date range used only the very first time the database is empty).
- **tariff-codes.json** — flat array of tariff codes to search for; edit this to change what the script pulls.
- **db.js** — Postgres access layer (`pg`), used both by the local scraper/migration scripts and by the deployed dashboard. Unlike the old SQLite version, the `importaciones` table schema is a **fixed column list** (`COLUMNS` constant) matching Daater's known export columns, plus derived `anio_mes` (`YYYY-MM`), `molecula`, `marca`, and `extraction_confidence` — Postgres needs `CREATE TABLE` up front, it can't grow columns from the first row inserted the way the SQLite version did. If Daater adds a new column to its Excel export, it's silently dropped by `replaceMonthData()` until someone adds it to `COLUMNS` by hand. `getPool()` lazily creates a single `pg.Pool` from `DATABASE_URL` (SSL required, `rejectUnauthorized: false` since Supabase uses a cert not in Node's default trust store by default in this setup). `ensureSchema()` runs `CREATE TABLE IF NOT EXISTS` + indexes on `anio_mes`/`molecula`. `getLatestMonth()` reads `MAX(anio_mes)`. `replaceMonthData()` does `DELETE` + re-`INSERT` for a given month inside a transaction — a month is always fully replaced, never merged, because Daater reports partial months that get completed over subsequent weeks and this avoids duplicate/stale rows. It batches inserts (`BATCH_SIZE = 500` rows per multi-row `INSERT ... VALUES (...), (...), ...`) rather than one `INSERT` per row — row-by-row inserts over a remote connection (Supabase) took minutes for a few thousand rows during the initial data migration; batching cut this drastically by trading round-trips for larger single statements (500 rows keeps well under Postgres's 65535-parameter-per-statement limit even with ~60 columns). It also runs each row's `Desc Completa De Producto` through `extractProductWithOverrides()` before insert, so every new weekly run gets molecula/marca automatically. `closePool()` must be called by one-shot CLI scripts (`search-daater.mjs`, `backfill-products.mjs`, `review-products.mjs`) so the Node process can exit; the long-running dashboard (`server.mjs`) never calls it.
- **product-extractor.js** — extracts `molecula` (active ingredient) and `marca` (brand name) from `Desc Completa De Producto`, which is free-text INVIMA regulatory boilerplate (250–5000 chars) with no fixed structure — at least 6 recurring sub-templates coexist (standard PRODUCTO/PRINCIPIO ACTIVO, RESOLUCION-first, "Cod. Producto:", medical-device/reagent PRODUCTO/COMPOSICION/USO, "MEDICAMENTO VITAL NO DISPONIBLE" named-patient imports, and unstructured narrative outliers) and the same tariff code can appear with any of them. Extraction is anchor-based (search for known field labels like "PRINCIPIO ACTIVO"/"NOMBRE DEL PRINCIPIO ACTIVO", accent/spelling variants included) rather than positional, with salt-prefix and dose stripping for molecula, and a fallback chain for marca (explicit `MARCA:` field → ®/™/© symbol next to the product name → null). Returns a confidence flag (`'high'`/`'low'`) per row so weak extractions can be found via `review-products.mjs`. Named-patient records ("MEDICAMENTO VITAL NO DISPONIBLE") get their embedded PII (patient name/ID) explicitly stripped from the output fields. `hashDescripcion()` hashes the exact description text (not `Numero Formulario`, since the same product description repeats across thousands of shipments) — this hash is the key used in `product-overrides.json`.
- **product-overrides.json** — manual corrections keyed by `hashDescripcion()` output; each entry can set `molecula` and/or `marca` and always wins over the regex result (`applyOverrides()`). Use `review-products.mjs` to find which hashes need an entry, add them here, then re-run `backfill-products.mjs` to apply.
- **backfill-products.mjs** — one-time-but-safe-to-rerun migration: recomputes `molecula`/`marca`/`extraction_confidence` for every row in the `importaciones` table. Re-run it after editing `product-overrides.json` or changing the extraction rules in `product-extractor.js`.
- **review-products.mjs** — reports the top N (by row count) distinct product descriptions whose extraction came out low-confidence, with the hash to use as a `product-overrides.json` key — the workflow for iteratively improving extraction accuracy over time.
- **server.mjs** / **public/index.html** / **public/app.js** — the dashboard. `server.mjs` exports an Express `app` (no top-level `listen()` call) and exposes JSON aggregation endpoints (`/api/summary`, `/api/by-molecula`, `/api/by-month`, `/api/by-tariff`, `/api/by-country`, `/api/by-importer`, `/api/molecula/:nombre` for the brand breakdown of one molecule, `/api/focus-molecules` to list the resolved focus set), all accepting optional `?from=YYYY-MM&to=YYYY-MM` filters plus `?focus=1` (see below). Numeric Daater columns are stored as TEXT with comma decimals, so every aggregation query does `REPLACE(x, ',', '.')::NUMERIC` (Postgres cast syntax, not SQLite's `CAST(... AS REAL)`). It only calls `app.listen()` when run directly (`node server.mjs`) — checked via `import.meta.url === pathToFileURL(process.argv[1]).href`, **not** a naive `` `file://${process.argv[1]}` `` string template, because on Windows `process.argv[1]` uses backslashes and lacks the `///` separator `import.meta.url` has, so a naive comparison silently never matches and the server exits immediately without arriving at `listen()` or logging anything. In Vercel, `api/index.js` imports and re-exports this same `app` as the serverless function handler, so `listen()` is never called there — Vercel's own runtime handles the HTTP listening. The front end is plain HTML/JS + Chart.js (no build step, no framework) — molecule view is the primary chart with click-to-drill-down into brand, plus a monthly time series and secondary tabs for tariff code/country/importer, each with a "Ver tabla" toggle for an accessible table view. Chart.js itself is vendored into `public/vendor/chart.js` (copied from `node_modules/chart.js/dist/chart.umd.min.js` via `npm run vendor-chart`) rather than served dynamically from `node_modules` — Vercel's serverless function bundler doesn't package `node_modules` files that are only referenced via a runtime filesystem path (as `express.static(path.join(__dirname, 'node_modules/...'))` did previously), so that route 404'd in production even though it worked locally. Re-run `npm run vendor-chart` after bumping the `chart.js` dependency.
- **focus-molecules.json** — hand-maintained list of `keywords` for molecules of particular interest to the company (e.g. `ECULIZUMAB`, `ANTITRIPSINA`, `IMIGLUCERASA`, `IDURSULFASA`). `molecula` values are free-text-derived and inconsistent (mixed case, dosage/form suffixes like `IMIGLUCERASA (400 U EXTRAIBLES)` vs `IMIGLUCERASA (DOSIS EXTRAIBLE 400U)`, accents), so matching is substring + accent/case-insensitive rather than exact — a keyword like `ANTITRIPSINA` matches `ALFA - 1 ANTITRIPSINA` too. `server.mjs` resolves keywords to the actual set of matching `molecula` values (against `SELECT DISTINCT molecula`) and caches the result in memory for `CACHE_TTL_MS` (5 minutes) rather than once at startup — a one-time startup cache doesn't fit a serverless deployment, where "startup" can recur on every cold invocation or never recur for a long-lived warm one. `dateFilter()` adds `molecula = ANY($n)` to every aggregation endpoint when the request includes `?focus=1` — so the "Solo moléculas de interés" checkbox in the dashboard filters the whole page, not just the molecule chart.
- **product-extractor.js** dosage-parenthetical stripping — `cleanMolecula()` strips trailing/embedded parentheses that are purely a dose/unit annotation (matching `UNIDADES`/`U`/`UI` with optional `DOSIS`/`EXTRAIBLE(S)`, e.g. `IMIGLUCERASA (400 U EXTRAIBLES)` and `IMIGLUCERASA (DOSIS EXTRAIBLE 400U)` both → `IMIGLUCERASA`), while leaving disambiguating parentheses alone (`ANIFROLUMAB (MEDI-546)`, `ADRENALINA (EPINEFRINA)`, `BICALUTAMIDA (FORMA H1)`) — the regex only matches on those specific unit/dose keywords, not on parentheses in general, since a blanket strip would destroy synonym/compound-code info that's genuinely part of the molecule name in this dataset.
- **xlsx-parser.js** — parses the downloaded `.xlsx` (via `xlsx`/SheetJS) into row objects keyed by column header, and groups them by `anio_mes` derived from the `Fecha` column (`YYYY-MM-DD`) — a single downloaded file can span multiple months.
- **search-daater.mjs** — the entire automation, structured as a linear sequence of Playwright steps:
  1. `login()` — fills credentials, waits for the sidebar combobox to confirm login succeeded.
  2. `selectCountry()` — picks the country from the sidebar dropdown; this determines which "bases" (period tabs) become available.
  3. Iterates base tabs (`getBaseTabs`), skipping any that don't match `config.baseFilter`.
  4. For each matching base: `selectFlowTab()` switches to imports or exports, `addTariffCodes()` types each code into the autocomplete and confirms it via keyboard (`ArrowDown`+`Enter` — **clicking the suggestion directly does not confirm selection in this widget**, only keyboard nav does), then verifies each code rendered as a confirmed chip. `ensureShowDetail()` reads the actual `aria-checked` state of the "Mostrar/Ocultar detalle" switch (the label text flips depending on state, so it can't be used to determine current state) and toggles it on if needed.
  5. `computeMonthsToFetch()` + `setDateRange()` fix the two `<input type="date">` fields (they live in the main filter panel, not the sidebar): if the master DB is empty, uses `config.backfillRange`; otherwise requests `[last loaded month, next month]` so a partially-loaded month gets re-pulled once Daater completes it, and any newly available month gets picked up.
  6. `clickSearch()` runs the query; `waitForResults()` polls the "N filas cargadas" text. This needed two waits, not one: it first waits for the count to *change* from its pre-search value (a stale count can otherwise be misread as the new result), then — because the count passes through a transient `"0"` for several seconds while the table is still loading — waits out a 10s grace period and requires the value to read the same on 3 consecutive 1s polls before accepting it as final.
  7. `downloadResults()` triggers the download button, saves the file as `daater_<país>_<flow>_<base>.xlsx` (slugified) into `outputDir` as a backup copy.
  8. The downloaded file is parsed and grouped by month, then each month is written to Supabase via `replaceMonthData()`.
  9. Prints a summary of row counts and file paths per base at the end.

All UI targeting is done via Playwright role/text locators (no test IDs available in the target app), so if Daater's UI changes, the brittle points to check first are: the sidebar combobox/tab roles, the `PARTIDA ARANCELARIA` label used to locate the tariff-code input, the "Mostrar/Ocultar detalle" switch, the two bare `input[type="date"]` fields, and the `filas cargadas` / `Descargar` text matches.

Output files (`output/*.xlsx`), the old local `daater.db` (kept around only as a pre-migration backup, no longer read by any script), and `.env.local` are gitignored; sample historical outputs may exist locally under `output/` but are not tracked. `product-overrides.json` is NOT gitignored — it's hand-maintained and should be kept in version control alongside the extraction rules it corrects. This project directory is not a git repository (no `.git`), so none of the above "gitignored" behavior is actually enforced by tooling right now — it just documents intent for whenever git is initialized.

## Deployment

The dashboard is deployed to Vercel as a serverless function so the wider org can view it, at `https://daater-dashboard-chi.vercel.app/` (project name `daater-dashboard` under the `juan-s-guzman-s-projects` team; Vercel picked the `-chi` suffix on the domain itself since `daater-dashboard.vercel.app` wasn't available at the time — check `vercel project inspect daater-dashboard` or the Vercel dashboard if this domain ever needs to be reconfirmed). The scraper keeps running locally exactly as described above (from a machine with Playwright/Chromium installed) and writes directly to Supabase over the network — there is no separate "sync" step, unlike the old Fly.io setup where a local SQLite file had to be uploaded after each run.

- **Supabase** (Postgres) is the single source of truth for `daater.db`'s old data — both the local scraper and the deployed dashboard connect to the same database via `DATABASE_URL`. There is no local database file in the new setup (aside from the retired `daater.db` kept as a backup).
- **api/index.js** — the Vercel serverless entrypoint: imports and re-exports the Express `app` from `server.mjs` unchanged (`export default app`). Vercel's Node runtime wraps it as a request handler.
- **vercel.json** — `framework: null` (attempts to stop Vercel's autodetection from locking the project to a generic "Express" preset). In practice, as of this setup, Vercel's CLI kept showing "Detected Express" and ran its own generic install step instead of the custom `installCommand` below, even on a freshly created project with `framework: null` already present in `vercel.json` before the first deploy — Playwright/Chromium still got installed during the Vercel build regardless. The dashboard works correctly despite this (it's just a slower build, ~30s+ extra download), but the `installCommand` below is not reliably honored — don't assume it is without checking a fresh build log. `installCommand` deletes `scripts.postinstall` and `dependencies.playwright` from `package.json` before running `npm install`, mirroring what the old Fly.io Dockerfile did — Playwright/Chromium is only needed for the local scraper, never for the deployed dashboard, when this actually takes effect. `rewrites` sends all `/api/*` requests to the `api/index.js` function; static files under `public/` are served by Vercel directly, not through Express.
- **.vercelignore** — excludes `node_modules`, `.env.local`, `output/`, and the retired `daater.db*` files from the deploy upload (this directory has no `.git`, so Vercel CLI can't infer what to skip from `.gitignore` the way a Git-integrated deploy would).
- **DATABASE_URL** — set as a Vercel production environment variable (`vercel env add DATABASE_URL production`), pointing at the Supabase pooler connection string (see the pooler note in Commands above — the direct-connection host does not work from Vercel).
- **Known fragility avoided**: the earlier Fly.io setup required uploading a ~70MB SQLite file over `flyctl sftp put` after every scraper run, which dropped mid-transfer repeatedly and once left the remote file corrupted (crash-looped the app with `SqliteError: database disk image is malformed`). Moving to Supabase/Postgres removes this whole class of problem — the scraper writes rows directly, there is no file to transfer.
